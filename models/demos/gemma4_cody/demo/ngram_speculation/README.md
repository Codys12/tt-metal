# Speculation POC for gemma4_cody

The "draft" half of speculative decoding that pairs with the packed-decode
verifier (Approach B, measured in
`models/demos/gemma4_cody/tests/unit/test_packed_decode_compare.py`).

Two drafters are available:

- **N-gram** (default, no model required) — Python lookup speculator.
  Floor for what's possible.
- **MTP** (Gemma's official assistant model) — small 4-layer Gemma
  variant trained specifically as a speculative-decode drafter. See
  https://ai.google.dev/gemma/docs/mtp/mtp. **Not installed by default**;
  see "Installing the MTP drafter" below.

## What's here

- `speculator.py` — `NGramSpeculator` class. Tracks recent k-grams in
  this request's history; proposes draft continuations when the last k
  tokens match an earlier prefix. Pure Python, ~100 lines, O(1) lookup.
- `mtp_drafter.py` — `MTPDrafter` class. Wraps Gemma's MTP assistant
  model with the same `observe()` / `propose()` interface. Pulls in
  `transformers` + `torch` only when instantiated.
- `demo.py` — runs either drafter against a real corpus tokenized with
  cody's Gemma4 BPE, simulates verify-and-accept against the corpus as
  ground truth, prints acceptance rate and projects end-to-end speedup
  using the measured packed-prep cost from Approach B.
- `__main__.py` — entry point so you can run
  `python -m models.demos.gemma4_cody.demo.ngram_speculation`.

## Installing the MTP drafter

The MTP assistant checkpoint is **not** in `/mnt/nas/gemma` (which holds
only the 60-layer target). Get it from HF Hub:

```bash
# Requires internet + ~1 GB disk. May need `huggingface-cli login` if the
# checkpoint is gated.
huggingface-cli download google/gemma-4-26B-A4B-it-assistant \
    --local-dir /mnt/nas/gemma-assistant
```

Then run the demo against it:

```bash
python -m models.demos.gemma4_cody.demo.ngram_speculation.demo \
    --drafter mtp --mtp-path /mnt/nas/gemma-assistant --t 4
```

For a corpus-aware comparison vs n-gram:

```bash
# n-gram baseline
python -m models.demos.gemma4_cody.demo.ngram_speculation.demo --t 4

# MTP drafter on same corpus
python -m models.demos.gemma4_cody.demo.ngram_speculation.demo \
    --drafter mtp --mtp-path /mnt/nas/gemma-assistant --t 4
```

Expected acceptance per Gemma 4 papers / literature:
- N-gram on code: ~30-40%
- MTP drafter: ~70-90%

Per the speedup table in `/tmp/packed_decode_comparison_summary.md`, MTP
acceptance puts you in the 2-5× speedup range depending on T.

## What it does and doesn't prove

**Does prove:**

- The n-gram algorithm is correct and runs in O(1) per propose call.
- The simulation produces real per-proposal acceptance rates against
  text generated by the actual Gemma4 BPE tokenizer.
- The projected end-to-end speedup, given an acceptance rate, is
  computed from the actual measured packed-prep cost (Approach B) on
  1×8 P150 — not invented numbers.

**Does NOT prove:**

- It does not run the Gemma4 model. The "verifier" is the corpus —
  i.e., we simulate "the model would have emitted exactly these
  tokens." Realistic acceptance on a *running* model may differ because
  Gemma4's generation patterns aren't perfectly captured by a static
  corpus.
- It does not run on real hardware. The packed-verifier cost (88 ms
  SDPA + 20.85 ms prep) is plugged into the speedup math as a measured
  constant.
- It does not handle KV cache rollback. The simulation just walks the
  corpus, but a real implementation must invalidate KV entries for
  rejected drafts before the next step.

## How acceptance rate determines speedup

```
single-token decode (baseline) ≈ 88 ms/token   →  ~11.4 tok/s/u

packed-verifier step (Approach B, T=4):
  prep:  20.85 ms (measured)
  SDPA:  ~88 ms  (assumed same as single-token; conservative)
  total: ~109 ms/step

  if all 4 drafts accepted: 4+1 = 5 tokens/step  →  ~46 tok/s/u  (4.0x)
  if 2 accepted (rate=50%): 2+1 = 3 tokens/step  →  ~28 tok/s/u  (2.4x)
  if 0 accepted (rate=0%):  0+1 = 1 token/step   →  ~9.2 tok/s/u  (0.8x — REGRESSION)
```

So the speculator has to be *right often enough* to amortize the bigger
step cost. The demo measures whether n-gram lookup clears that bar.

## How to extend into production cody

This is the algorithm; the integration work is bounded scope:

1. **Per-slot speculator state.** Add a `_NGramSpeculator` instance to
   each `_Slot` in `server.py`. Reset it in
   `_release_slot_pages(slot)` so a freed slot doesn't leak
   n-grams into the next request.
2. **Wire `observe()` into the decode emit path.** In `_step_decode`
   at `server.py:~1247`, after `slot.all_tokens.append(tok)`, call
   `slot.speculator.observe([tok])`.
3. **Wire `propose()` into the input build.** Before constructing the
   single-token input for the next step, call `slot.speculator.propose()`
   per slot. If any slot returns a draft, switch the next step from
   `_step_decode` (single-token) to `_step_decode_packed(T)` (Approach B
   verifier with packed Q + per-(slot, token) causal mask).
4. **Accept/reject after the verifier.** Compare the verifier's
   per-(slot, token) sampled outputs against the proposed drafts. Find
   the first mismatch per slot. Emit accepted-prefix + one bonus
   token. Roll back KV cache positions ≥ first-mismatch by either:
   - Letting `paged_update_cache` overwrite them on the next step
     (KV positions are write-once-per-step, and `cur_pos` rewinds
     to the first-rejected position).
   - Or explicitly invalidating with a scratch-write.
5. **Track per-request stats.** Expose acceptance rate per request
   so you can monitor production speculator quality, and decide
   when to disable speculation for a slot if the rate falls below a
   threshold (e.g., < 20% — the regression line above).

## Algorithm tuning notes

- **k (ngram_size) too small** (e.g., 1): high hit rate but low
  per-proposal acceptance — many false-positive matches.
- **k too large** (e.g., 6+): low hit rate, but matches that hit are
  almost always correct.
- **T (num_drafts) too large** wastes verifier compute on tokens
  unlikely to be accepted; T=4 is a typical sweet spot.
- **min_hits > 1** filters out singleton k-grams that occur once and
  never again. Reduces speculator false positives but reduces hit rate
  on novel content.

The demo's `--sweep` mode tries (k, T) ∈ {2,3,4,5} × {2,4,8} and
reports the configuration that gives the largest projected speedup
on your specific corpus.
